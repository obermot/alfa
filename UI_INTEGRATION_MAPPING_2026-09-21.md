# Незабудка — UI → logic mapping

Дата: 2026-09-21
Статус: рабочая карта переноса утверждённого UI поверх проверенного ядра 0.2.5.

## Принцип
Визуальный слой переносится без замены проверенной reminder-архитектуры. AlarmManager, Room v2, ReminderScheduler, RecoveryReceiver, audio focus, TTS и рабочий ACK сохраняются, пока новый UI не требует строго необходимого изменения.

## Экран 1 — Главный
Источник данных: ReminderDao.active().
Создание: существующий handle() → TemporalParser → createReminder().
Голос: существующий startListen(); системный SpeechRecognizer с Vosk fallback.
Строка reminder открывает экран 2.
Нижняя навигация: Напоминания / История / Настройки.
Старые глобальные controls не переносятся.

## Экран 2 — Просмотр / редактирование
Сущность: ReminderEntity.
Что напомнить: ReminderEntity.text.
Когда напомнить: dueAt/originalDueAt.
Повторять: отдельное recurrence, не retry.
Громкость и заметка требуют отдельного хранения; не подменять их существующим repeatIntervalMinutes.
Удаление: подтверждение → cancel scheduler/notification → удалить/деактивировать сущность согласно новой модели.

## Экран 3 — Дата, время и recurrence
Новый UI не должен использовать repeatIntervalMinutes как recurrence.
Требуется модель выбранных дат/времён, включая несколько дат. Это изменение data layer, поэтому реализуется отдельно с миграцией без destructive reset.
Старые варианты по будням/выходным/неделям не возвращать.

## Экран 6 — Сигнал
Основа: существующая AlarmActivity + AlarmReceiver.
Сохраняются: full-screen/lock-screen behavior, audio focus, TTS, voice ACK infrastructure.
Новый UX: текст сигнала; Напомнить снова; Удалить напоминание; закрытие X/свайп.
ACK-инфраструктуру не удалять, даже если визуальное управление меняется.

## Экран 7 — Напомнить снова
Это snooze, а не recurrence и не автоматический retry.
Быстрые варианты: 5/10/30 минут/1 час + Другое время.
Другое время: часы/минуты на том же экране.
Базовое расписание reminder не менять.

## Экран 8 — История
Нужен event/history store. Текущая Room v2 хранит reminder state, но не достаточную историю событий.
Статусы должны отражать только известное приложению взаимодействие.

## Экран 9 — Пропущено
Системное notification.
Новая retry-policy: основной сигнал; 3×5 минут; 3×10 минут при полном отсутствии взаимодействия; затем missed.
Это отдельная механика от recurrence и snooze.

## Порядок реализации
1. Новый shell/главный экран и навигация поверх текущего ядра.
2. Экран просмотра/редактирования и подтверждение удаления.
3. Новая recurrence/date model с безопасной Room migration.
4. Новый Alarm Screen + отдельный snooze screen при сохранении ACK plumbing.
5. Event history и missed/retry state machine.
6. Проверка компиляции.
7. Один build trigger.
8. Телефонный тест и запись результата в TEST_HISTORY.md.

## Запреты
Не делать destructive Room migration.
Не менять signing identity.
Не смешивать recurrence, retry-on-no-interaction и snooze.
Не запускать Actions после промежуточных коммитов.
Не считать функцию проверенной на телефоне до подтверждения пользователя.
